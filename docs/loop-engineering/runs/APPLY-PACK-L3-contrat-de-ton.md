## Deviation from FEATURE_APPLY_PACK.md's L3 wording (flagged, not silent)

FEATURE_APPLY_PACK.md's L3 acceptance criteria (as handed to this loop) say "same select/insert/update/delete pattern as `cv_variants`." This loop implements a **narrower** grant instead: `authenticated` gets ONLY `select` and `insert` on `tone_contracts` — no `update`, no `delete`. Rationale: the acceptance criteria in the same document also require "publishing a new tone-contract version never mutates a past version in place," and a 4-verb grant makes that an app-code promise, not a database guarantee — any future code path (a bugfix, a bulk-edit feature, an admin shortcut) could `UPDATE tone_contracts SET ...` and silently rewrite history under RLS's nose. Revoking UPDATE/DELETE from `authenticated` makes the immutability structural: even a compromised or careless app-code path gets 42501, proven by the pgTAP suite. `service_role` keeps full DML for legitimate ops/admin correction, exactly as `cv_variants` grants it.

This is a **declared deviation requiring explicit reviewer/founder sign-off** before merge — flagged in `tasks/FEATURE_APPLY_PACK.md`'s L3 acceptance criteria section too. If the founder prefers the literal 4-verb pattern (accepting that immutability then rests on app discipline alone), that is a one-line grant change plus dropping two `throws_ok` assertions in the pgTAP suite — not a schema rewrite.
